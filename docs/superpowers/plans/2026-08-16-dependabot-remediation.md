# Dependabot Remediation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Resolve all 31 open GitHub Dependabot alerts (1 critical, 12 high, 14 moderate, 4 low) on `main` before closing M5, per issue #137, without breaking any existing build or test.

**Architecture:** Two direct-dependency version bumps (`next` in `apps/web`, `nodemailer` in `apps/api`) plus a root-level npm `overrides` block that forces patched versions for six transitive-only vulnerable packages (`body-parser`, `qs`, `path-to-regexp`, `shell-quote`, `lodash`, `esbuild`) whose immediate parents (`express@5.2.1`, `concurrently@9.2.1`, `express-validator@7.3.1`, `tsup@8.5.1`/`vite@8.2.1`) are already at their own latest release and have not yet republished with patched sub-dependencies.

**Tech Stack:** npm workspaces (root + `apps/api`, `apps/web`, `packages/shared`), npm `overrides` field, existing Vitest/Next/Prisma/Docker verification pipeline (no new tooling).

## Global Constraints

- Every vulnerable package identified by `npm audit --json` and cross-referenced against the 31 GitHub Dependabot alerts must end at or above its `first_patched_version`.
- No `package.json` semver range may be loosened beyond what's needed to reach the patched version (e.g. `next` stays pinned to a specific `16.x` version with `^`, not opened to `*`).
- These are dependency-version changes, not new application behavior, so there are no new unit tests to write test-first. Each task's "test cycle" is: run the existing automated suite scoped to the affected workspace, then (in the final task) the complete repository verification pipeline from `docs/superpowers/specs/2026-08-15-revenue-sharing-ledger-design.md` / Task 6 of the ledger plan (API tests, web tests, shared build, web build, Docker build, Prisma migration status).
- Local Docker daemon is only reachable via `docker.exe` (Docker Desktop) in this WSL environment — `docker compose` from the WSL socket fails; use `docker.exe compose`.
- Test database: `postgres-test` service from `docker-compose.yml`, reachable at `postgresql://admin:password@localhost:5433/blinkfy_test` once `docker.exe compose up -d postgres-test` is running (already up from prior work in this session; if not, bring it up before Task 3).
- Branch: `security/dependabot-remediation-137` (already created off `main` at commit `9ebe0c9`).

### Task 2: Transitive dependency remediation via npm `overrides`

**Files:**
- Modify: `package.json` (root)
- Modify: `package-lock.json` (regenerated by `npm install`)

**Interfaces:**
- Produces: a root-level `overrides` block forcing `body-parser@^2.3.0`, `qs@^6.15.3`, `path-to-regexp@^8.4.2`, `shell-quote@^1.10.0`, `lodash@^4.18.1`, `esbuild@^0.28.2` across the whole dependency tree, resolving GH alerts #1/#43 (`qs`), #23/#24 (`path-to-regexp`), #25/#26 (`lodash`), #44/#55 (`shell-quote`), #45 (`esbuild`), #54 (`body-parser`).
- Consumes: none of these six packages are imported directly by application code (confirmed via `npm ls <pkg>` in this session — each is pulled in only by `express@5.2.1` → `body-parser`/`qs`/`path-to-regexp`; `concurrently@9.2.1` → `shell-quote`; `express-validator@7.3.1` → `lodash`; `tsup@8.5.1`/`vite@8.2.1` → `esbuild`), so no application source file changes.

- [ ] **Step 1: Add the `overrides` block to the root `package.json`**

Add a new top-level key after `"devDependencies"`:
```json
"overrides": {
  "body-parser": "^2.3.0",
  "qs": "^6.15.3",
  "path-to-regexp": "^8.4.2",
  "shell-quote": "^1.10.0",
  "lodash": "^4.18.1",
  "esbuild": "^0.28.2"
}
```

- [ ] **Step 2: Install and confirm every overridden package resolved**

Run: `npm install`

Expected: exits `0`. Then:
```bash
npm ls body-parser qs path-to-regexp shell-quote lodash esbuild
```
shows only the target versions (or higher within the same major) everywhere they appear — no line shows `body-parser@2.2.2`, `qs@6.14.1`, `path-to-regexp@8.3.0`, `shell-quote@1.8.3`, `lodash@4.17.23`, or `esbuild@0.27.3`.

- [ ] **Step 3: Confirm `concurrently` and the dev script still load correctly**

Run: `node -e "require('concurrently'); console.log('concurrently loads OK')"`

Expected: prints `concurrently loads OK` and exits `0` — proves the forced `shell-quote@^1.10.0` didn't break `concurrently`'s own `require` graph (shell-quote's public `quote()`/`parse()` API is unchanged across `1.x`, so this is the practical smoke check available without launching the long-running `npm run dev` dev-server script).
